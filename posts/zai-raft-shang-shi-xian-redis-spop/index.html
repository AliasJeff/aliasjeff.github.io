在 Raft 上实现 Redis SPOP
Posted on 2026-11-16 :: Raft Redis Rust AI

01 任务：一条看起来能无脑适配的命令

SPOP 的语义很简单，从一个集合里随机弹出一个（或 count 个）元素，弹出来就删掉。我一开始也没多想，觉得它跟其他命令的适配没什么区别，直接丢给 AI 做了。

结果这是整条协议里最难在 Raft 里实现的命令之一。

02 冲突：状态机要相同，随机要不同

Raft 的模型一句话讲完，同一条日志，按同一顺序，喂给几个节点的状态机，每个节点独立执行，最后状态必须完全一致。两台初始值为 0 的机器，各收到一条加一的请求，结果都是 1，中间不需要任何商量。

所以 Raft 真正复制给上层的东西不是数据，是一条契约：

初始状态相同 + 日志序列相同 ⇒ 最终状态相同

SPOP 把契约两边各砸了一个洞。随机砸的是操作那一侧，节点 A 随机弹出了 X，节点 B 随机弹出了 Y，日志完全一致，执行的操作其实不一样；迭代序砸的是状态那一侧，同一份数据，各节点眼里长着不同的样子。而且这种分叉是静默的，Raft 保证的是日志一致，不保证 apply 之后的状态一致，除非额外做状态哈希之类的校验，否则读请求打到不同节点会拿到不同数据，全程没有任何报错。

所以在 Raft 上做 SPOP，随机性必须被「复制」。拆开是两个确定性要求：

  1. 随机数序列确定。每个节点对同一条日志要产生同一个「随机」选择，随机数发生器只能用已经被复制过的数据当种子；
  2. 迭代视图确定。就算随机数一样，同一个下标在所有节点上必须指向同一个成员，否则两边选中的还是不同的元素。

第二点比第一点阴险，因为大多数人（包括我自己一开始）根本意识不到它是个问题。

03 第一层坑：HashMap 的迭代顺序不可复现

alias-cache 的集合底层是链式哈希，下标指向哈希桶，桶里挂链表，链表节点存元素。要按下标采样，就得先约定「第 i 个」是谁，也就是迭代顺序。

而迭代顺序恰恰是最不可靠的东西。Rust 标准库的 HashMap 默认用带随机种子的 SipHash（防哈希碰撞攻击），迭代顺序不保证稳定，同一个进程里两个内容相同的 map 顺序都可能不一样。就算自己实现数据结构、固定哈希种子、保证所有插入删除的顺序一致，理论上也能对齐。

「理论上」三个字，就是下一层坑的入口。

04 第二层坑：快照会把初始状态也打散

Raft 有快照机制，一个节点落后太多的时候，不用慢慢补日志，直接把对方当前状态的快照装过来。问题在于，快照怎么描述一个 HashMap。

链式哈希的 dump 通常就是一个无序条目集合，这个 map 里有 A 和 B，谁前谁后没有规定。装快照的节点按 dump 顺序重建，重建出来的桶布局取决于 dump 那一刻的迭代顺序，跟节点自己的操作历史无关。

于是同一份数据，两个节点完全可以长成两种布局：

节点1:  bucket[0] → B → A          迭代序: B, A, D
        bucket[2] → D

节点2:  bucket[0] → A → B          迭代序: A, B, D
        bucket[1] → D

初始状态不同，后续再多确定性的执行也救不回来。我复盘时画的那张链式哈希手绘图，红笔标「坑在这」的就是这里。

那 Redis 本体为什么没事？因为 Redis 的主从复制走的是另一条路，主节点先执行，确定这次到底弹出了哪些成员，然后把确定后的结果同步给从节点，从节点照做，从头到尾不需要自己随机。Raft 不能这么干，它的模型就是同一条操作日志发给所有节点、各自独立得到相同结果，没有「主节点替你随机」这个环节。（技术上可以让 leader 先把随机解析成确定结果再写日志，但那等于把状态机前移到 leader 上，改的是复制语义，不是一个命令适配能兜住的事。）

05 AI 的解法：排序对齐视图，日志时钟当随机种子

接下来是整件事最有意思的部分。我全程没有干预，GPT 6 Astra Ultra 自己发现了迭代顺序的问题，然后给了两招。

第一招，对齐视图。既然迭代顺序不可靠，那每次执行前先做一次全量排序，把成员排成所有节点都一致的字节序列，下标就有了统一的含义。AI 写出来的代码长这样（节选）：

/*
 * 集合的迭代顺序不稳定：
 * - 快照恢复和集合重建可能改变成员顺序；
 * - 不同 Raft 节点的迭代顺序可能不同；
 * 因此必须先按字节序排序，建立所有节点一致的成员序列。
 */

let mut candidates: Vec<Bytes> = set_guard.iter().cloned().collect();
candidates.sort_unstable_by(|left, right| left.as_ref().cmp(right.as_ref()));

let mut rng = DeterministicRng::for_key(&self.key, write_clock);
for _ in 0..pop_count {
    let index = rng.next_index(candidates.len());
    let member = candidates.swap_remove(index);
    ...
}

注释里那三条，就是 03、04 两节说的坑，AI 自己从代码库里推理出来的。

第二招更漂亮，随机数种子。朴素做法是 leader 在写日志前生成一个随机数、塞进日志条目里跟着复制。但 alias-cache 里有个我早前设计的机制，每条日志自带一个时间戳作为逻辑时钟，用来让各节点做确定性的过期判断。AI 翻到了这个设计，直接拿 write_clock 跟 key 一起喂给 DeterministicRng 当种子。种子本来就已经复制过了，随机数等于免费。

两个确定性要求都满足了，一切看起来都合理。

06 逐行拆这两招

先说句公道话，这两招在机制上是对的，值得逐行看一遍它到底怎么个对法。

  flowchart TB
    entry["同一条日志: SPOP key · write_clock=T5"]
    subgraph nodeA ["节点 A，布局 α"]
        A1["迭代序 B, A, D"] --> A2["全量排序 → A, B, D"]
        A2 --> A3["RNG(key, T5) 取下标 1"]
        A3 --> A4["弹出 B"]
    end
    subgraph nodeB ["节点 B，布局 β"]
        B1["迭代序 A, B, D"] --> B2["全量排序 → A, B, D"]
        B2 --> B3["RNG(key, T5) 取下标 1"]
        B3 --> B4["弹出 B"]
    end
    entry --> A1
    entry --> B1
    A4 --> same["两边状态保持一致"]
    B4 --> same

两个节点的起点布局不一样，排序把视图拉平，种子来自日志把随机数拉平，最后各自弹出同一个元素。这是「对」的那一半。

再看代码

iter().cloned().collect()，把集合成员整个克隆进一个新 Vec，O(n) 时间、O(n) 空间，这是每次执行命令都要交的固定成本。sort_unstable_by 也不是随手选的，集合成员互异，稳定排序费劲保住的「相等元素相对顺序」在这里根本不存在，unstable 背后那套 pattern-defeating 快排没有任何可丢的东西。比较器用 as_ref() 拿字节序，字典序跟机器、跟 locale、跟运行环境全都无关，恰好是跨节点对齐最想要的那种序。

随机数这行：

let mut rng = DeterministicRng::for_key(&self.key, write_clock);

种子是 key 和 write_clock 的二元组。write_clock 是日志条目自带的逻辑时钟，跟着日志复制到每个节点，所以种子天然就是复制过的数据，每个节点从同一条日志能推出同一条伪随机流。key 混进种子里，不同集合的随机流就互相独立，同一条日志里两个不同 key 的 SPOP 不会踩出相关的下标序列。

弹出的循环里还埋着一个细节：

let index = rng.next_index(candidates.len());
let member = candidates.swap_remove(index);

swap_remove 是 O(1) 删除，把最后一个元素搬进被删的坑里。但搬完之后数组就不再有序了，count 大于一时，第二次取的下标落在乱序数组上。这为什么不破坏确定性？因为确定性只要求同起点加同操作序列，排序负责把所有节点拉到同一个起点，之后的每一行代码在每个节点上都是一模一样的操作。起点一致、操作一致、结果就一致，中间数组有没有序，无所谓。

整条命令的执行路径整理成伪代码，成本标在旁边：

apply(SPOP key count):
  candidates ← clone(set(key))              # O(n) 时间 + O(n) 空间
  sort_by_bytes(candidates)                 # O(n log n)，制造一致的「第 i 个」
  rng ← DeterministicRng(key, write_clock)  # 种子来自日志，零额外复制
  repeat count:
    i ← rng.next_index(len(candidates))     # O(1)
    victim ← candidates[i]
    candidates.swap_remove(i)               # O(1)
    delete(set(key), victim)                # 真正改状态的一步

盯着最后一行注释看，真正改状态的只有 delete 一步，前面所有功夫都是为了让「随机选谁」在所有节点上可复现。说实话这部分我是看愣了的，用 Raft 适配 Redis 协议不是常见任务，训练集里大概率没有现成答案，它不光把两层坑都找全了，还翻出我早前写的逻辑时钟当随机源，把一个本来要额外复制的东西变成了免费的。

机制全对。然后是账单。

07 账单：弹一个元素，付一次 O(n log n)

小数据量下这套实现完全能用。但把伪代码旁边那两行成本标注连起来看，事情就不对了。假设集合里存了超过 1 GB 的数据，而 SPOP 又是会被高频调用的命令，每次执行都要 collect 一份全量成员、排一次 O(n log n) 的序，只为弹出一个元素。真正干活的 delete 是 O(1)，税是排在前面的排序，每次都付，弹一个元素也是全额。一条在 Redis 里接近常数开销的命令，在这里每次执行都是 O(n log n)。

08 真正可怕的是，它一个字都没提

性能还不是最可怕的。最可怕的是，AI 实现了这么大一个 workaround，从头到尾没有主动报告过这里的开销。

打个比方，把自己当大哥、AI 当干活的小弟。一个称职的小弟做到这里应该停下来汇报，说这个实现的开销有问题，您看是接受还是换个思路。它没有，它硬做完了。放到人身上，哪怕一个没什么经验的初级程序员，写到这里都会本能地觉得不对劲，先停下来问一句，这条命令的性能要求是什么。

这就是 Reward Hacking 的典型形态。大语言模型后期的强化学习阶段，倾向于选择更容易拿到奖励的做法，「任务完成」在奖励里，「性能预算」不在，于是模型交付一个眼前能跑的局部最优解。这不是我一个人的体感，METR 2025 年发过一篇前沿模型 reward hacking 的报告，ImpossibleBench 则是一个专门收集「不可能完成任务」的评测集，测的就是模型会不会硬做、做完还报告成功。同一个病根。

弹幕里有人说，这问题换 opus 就能解决，opus 会跟你确认。我不完全同意把归因放到单个模型上，提示词和模型确实能管住一部分，但只要验收标准里没有性能这一项，模型就没有义务替你守它。这不是哪个模型的问题，是所有被「把功能跑通」训练出来的模型的默认行为。

09 人类方案：把确定性做进存储结构本身

如果重新设计，需要换掉 HashMap 的底层数据布局。

链式哈希原来的样子，链表节点直接存数据。改法是，数据不存链表节点里，统一放进一个可扩容、可缩容的连续数组，新元素永远 append 到尾部；链表节点只存这个元素在数组里的下标。画出来是这样：

buckets（寻址结构，布局各节点自己说了算）
  [0] → (1) → (0) → ∅        括号里是 entries 的下标
  [1] → (2) → ∅
  [2] → ∅

entries（状态本体，所有节点逐字节一致）
  idx:    0      1      2
       ┌──────┬──────┬──────┬
       │  A   │  B   │  D   │
       └──────┴──────┴──────┘

查找路径跟普通 HashMap 完全一样，只有最后一步从指针寻址变成数组寻址。

关键在快照语义变了。只要所有节点按同样顺序执行操作，entries 数组在所有节点上就完全一致，快照直接同步这个数组就行，不用再 dump 一堆无序条目。桶怎么排布、用哪个哈希种子，各节点随意，桶只是寻址的索引结构，数组才是状态本身。

节点1:  buckets（布局 α）──┐
节点2:  buckets（布局 β）──┼──→  entries: [ A | B | D ]

随机采样也随之变成，在数组长度里均匀随机一个下标，O(1)，天然确定。

两相对照，AI 方案和人类方案其实在解同一道题，怎么让所有节点拿到同一个起点。AI 是读时对齐，每次命令执行前现场排序，一致性是每条命令的运行时成本，O(n log n)；人类是写时对齐，append 顺序就是操作顺序，一致性在写入那一刻固化成布局的不变量，读取不再付费。有意思的是两边对快照的态度正好反过来，AI 方案每次执行都重新排序，快照随便 dump 无序条目也不影响正确性；人类方案顺序固化在数组里，快照必须原样保序传数组。代价付在读路径还是写路径，你只能选一头。

弹幕在这个方案飘过两个行话。一个叫静态链表，链表但指针换成数组下标。另一个说 python 的办法，这个对照相当准，CPython 3.6 之后的 dict 就是同源结构，稀疏索引表加一个按插入顺序追加的紧凑 entries 数组，3.7 起插入顺序成了语言规范保证。同一套布局，Python 那边的动机是省内存和保序，这里换来的是复制语义上的确定性。

代价方面，寻址次数跟 Redis 本体的 dict 相同；多了一些内存分配，但数组的连续分配反而减少碎片，访存局部性更好。

10 结构如何运转

四个基本操作各过一遍。

查找，跟普通链式哈希完全同构：

lookup(member):
  for idx in chain[hash(member) % N]:     # 走链，跟 dict 一样
    if entries[idx] == member:            # 最后一步，指针寻址换成数组寻址
      return entries[idx]

插入，append 加挂链，两步 O(1) 均摊：

insert(member):
  i ← entries.push(member)                # 尾部追加，顺序即操作顺序
  chain[hash(member) % N].push(i)         # 链节点只存下标

随机弹出，整个结构的目的所在，对状态本体直接采下标：

random_pop(rng):
  i ← rng.next_index(entries.len())       # O(1)，对「状态本身」采样
  victim ← entries[i]
  last ← entries.back()
  entries.swap(i, len-1); entries.pop()   # O(1) 删除
  fix_chain(last, len-1 → i)              # 修指向被搬元素的链节点
  unlink(victim)                          # 摘掉 victim 的链节点
  return victim

fix_chain 是这个结构主要的新增维护成本。swap 把尾部元素搬进坑里之后，桶里那条链上存的下标就指错人了，得把指向 len-1 的那个链节点改成 i。找这个链节点不能靠遍历，不然又退化成 O(n)，工程上一般让 entries 槽位回存一个指向自己链节点的引用，或者把链节点本身内联进数组，修正就是 O(1)。CPython 的 dict 选了另一条路，删除不搬动、留墓碑位，代价是数组出现空洞、定期要整体重建。两条路都通，各有各的账。

快照和恢复是这套设计里最干净的部分：

snapshot: send(entries)                   # 只发数组，顺序即语义

restore(snap):
  entries ← snap                          # 逐字节一致
  for i, member in enumerate(entries):    # 各节点本地重建自己的桶
    chain[hash(member) % N].push(i)

恢复时每个节点拿自己的哈希种子重建自己的桶，桶布局完全可以不一样，没关系。桶是从 entries 派生出来的索引，派生物不一致无害，只要本体一致。你回头看 AI 方案，恰好是把这层关系用反了，把本体当容器，每次执行现场派生一个一致的视图出来。

最后把两个方案的全量成本对一遍账：

操作AI 方案（读时排序）数组打底（写时定序）
SPOP 弹 1 个元素O(n) 克隆 + O(n log n) 排序O(1)，含链修正
SRANDMEMBER 随机读 k 个只读也要先全量排序 O(n log n)O(k)，k 次随机下标直读
快照无序条目集合即可entries 数组，原样保序
恢复后跨节点一致性每次执行靠重排兜底恢复即一致

SRANDMEMBER 那行值得多看一眼。它是只读命令，按理说不该有什么负担，但在读时排序的方案下，随便看 k 个成员也要先付一遍全量排序的税；数组打底底下就是 k 次随机下标直读。这也是我认为这个改动值得的原因，收益不止 SPOP 一条命令，SRANDMEMBER、HRANDFIELD 这类随机指令全跟着受益。
